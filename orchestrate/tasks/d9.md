## Scope (D9, all seven features)

Record decision D9 in the decision log (section 10, a D9 row plus
D9a sub-rows where a design choice needs one) and add section 14
with the per-feature designs, following the style of section 13.

1. Table values. A `Value::Table` variant holding ordered
   key-value pairs (the key is a value, usually a char_string).
   Tables parse only in the 2.0 dialect. The 2.0 unquoted-value
   restriction keeps `{` and `}` illegal inside unquoted 2.0
   values. Canonical JSON gains one value kind under schema
   version 2: `{"kind": "table", "pairs": [{"key": <value>,
   "value": <value>}]}` (pairs, not an object: keys are arbitrary
   strings, order must survive). A `Display` round trip formats
   the table back to the 2.0 lexical form. No core dictionary
   item uses a table (roadmap 13.2), so no src/data_dict change.
2. Triple-quoted strings. `"""..."""` and `'''...'''` forms,
   multiline, parse only in the 2.0 dialect. The value is the
   content between the delimiters. Confirm the semantics against
   the 2.0 EBNF (roadmap 13.2 names the source) and the upstream
   cif_api reference. The canonical kind stays `char_string`.
3. Nested save frames. In the 2.0 dialect a save frame may hold
   data items and save frames. The IR (`SaveFrame`,
   src/grammar/structures/save_frame.rs) gains frame members.
   Canonical JSON: keep the existing frame object shape. Add a
   `frames` array to a frame object only when it holds nested
   frames. An empty or absent `frames` key keeps every existing
   2.0 expected pin byte-identical. Record the chosen shape in
   section 14.
4. Comments and text members inside lists. The 2.0 list
   production accepts a `#` comment between values and a `;`
   semi-enclosed text field as a list member. The canonical
   value kind for the text member is the existing `text_field`
   kind. The 1.1 list behavior is unchanged.
5. Unicode. In the 2.0 dialect, non-ASCII UTF-8 is legal in
   block codes, frame codes, item names, values, and comments.
   The 1.1 dialect keeps the ASCII character set. No canonical
   JSON change.
6. VT and FF line terminators. VT (`0x0B`) and FF (`0x0C`) act
   as newlines in the parser's line rule (they end the current
   line and open a value or comment position). The IUCr 2.0
   grammar lists VT and FF in its white space set. The 1.1 spec
   paragraph 23 defines white space as space, tab, and newline.
   The upstream cif_api accepts VT and FF even in a 1.1 file
   (`10.cif` carries no 2.0 magic). Decision D9a: support VT and
   FF in every dialect and record this as a 1.1 deviation,
   following the bracket-lead deviation precedent (section 13.3,
   In item 2, pinned by fixture 17). Also check the `1.25e+03`
   exponent form in `10.cif` against the 1.1 numeric grammar and
   record the outcome in section 14.

Out of scope: other 2.0 syntax not pinned by a known_gap file
(the bracket and brace container names already parse,
`container_names.cif` pins them). No new dictionary items. No
other IUCr dictionaries.
