## Part 1: the codegen step (decision D4, roadmap section 8)

Build the codegen step that later tiers reuse:

1. An annotation file you design and commit (for example
   codegen/annotations.toml, one section per item: the Rust variant
   name, the value type (string, numeric, a closed code set with
   its values, or a range with min/max), and any notes). The
   inventory in tests/dict_inventory.json drives the item list;
   the annotations drive the output.
2. A generator you can run with cargo (an example or a bin target,
   for example `cargo run --example dict_codegen`). It reads the
   inventory plus the annotations and emits the typed category
   modules under src/data_dict/core_cif/<category>/mod.rs,
   following the exact conventions of src/data_dict/core_cif/cell/mod.rs
   (enum + CifTerm + SingleValueTerm/LoopValueTerm + Display,
   typed enums for closed code sets, write-time range checks).
3. docs/codegen.md: how to add annotations for new categories and
   regenerate. The T5 tier (diffrn categories) reuses this step,
   so the document must be precise: annotation format, generator
   invocation, what gets overwritten, what is append-only
   (the pub mod lines in core_cif/mod.rs, the tag registry list).
4. No new external dependencies. The generator is plain Rust
   (read the JSON with serde_json, which is already a dependency).
